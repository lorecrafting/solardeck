# AUDIT 4 — Buildability, Supply, Reliability, and Coverage

Written 2026-10-20 13:40 UTC in the Pi harness by openrouter/deepseek/deepseek-v4.1-flash-1017

Fourth and last audit before the external review. Audits 1–3 asked *is the documentation true*, *will it
last 30 years*, and *is the hardware sound*. This one asks the question that decides whether any of that
matters: **can this be built, bought, supported, and does anything prove it works?**

Verdict up front: the design is coherent and the documentation is now internally honest, but **the
project is a spec, not a product**, and three findings are genuine showstoppers that no amount of
further documentation will fix.

---

## 1. Findings, ordered by severity

### F1 — The compute module has a 9-year runway against a 30-year claim ❌

| Fact | Value | Source |
| :--- | :--- | :--- |
| CM4 production commitment | **until at least January 2034** | Raspberry Pi obsolescence statement |
| Design life claimed | **30 years (to ~2056)** | `LONGEVITY_30Y.md` |
| Shortfall | **22 years** | arithmetic |

Nothing in the repo mentioned this. `HARDWARE_SPEC.md` §2.25 talks about dual-footprints "to prevent
obsolescence", but no part carries an EOL date, no second source is named, and there is no
module-replacement strategy.

Good news, verified externally: **IT8951 is Active** (ITE has issued no EOL/NRND), **BQ25895 is Active**,
CM4 is Active until 2034. So today's risk is not availability, it is *2034*.

**Mitigation adopted (ADR-023):** the CM4 is treated as a **field-replaceable socketed module**, not a
soldered brain. The carrier publishes a documented pinout contract (already in `FIRMWARE_INTERFACE.md`
for the RP2350; the CM4 side needs the same), three spare modules are bought at build time, and the
carrier keeps a **CM5-compatible footprint escape** so a successor module has somewhere to land.
Single-source parts are now listed in `spec_values.supply_chain` so a reviewer can see them in one place:
IT8951 (no second source at all), Kaleido panel, CM4, RP2350.

### F2 — Zero test points on a 6-layer board ❌

`grep -ci "test.?point|TP[0-9]"` over every `.kicad_sch` returns **0**. `HARDWARE_SPEC.md` mentions test
points 4 times in prose and none of them is a requirement. A board with no test points cannot be
brought up (F1's whole workflow), reworked (a 0.4 mm BGA reflow), or production-tested. Every audit so
far assumed "we'll probe it" without any place to probe.

**Mitigation adopted:** `HARDWARE_SPEC.md` §7.8 defines a **minimum test-point set** (14 nets, 1.0 mm
pads, one per rail plus bus-level probes), and Phase 16 requires the section to exist. This is a
schematic-capture requirement, not a new part.

### F3 — 5 % of catalogued features have any executable proof ❌

| Metric | Value |
| :--- | ---: |
| Catalogued features (`STATUS.md`) | 74 |
| Status `measured` | **0** |
| Features with any test at all | ~4 (2 daemons, 1 firmware state machine, 1 wire test) |
| Daemons specified / implemented | 41 / 2 |
| Test files / product code | 4 / ~1,900 LoC |
| Doc lines / code lines | 6,654 / 1,900 (**3.5 : 1**) |

The 3.5:1 ratio is the honest headline of this audit. **This repo is a specification, not a product.**
That is a legitimate stage, and the docs are now unusually honest about it (`STATUS.md` says `measured:
0` in bold). But it means the binding constraint is **electronics-engineering hours and a dev kit**, not
ideas. The marginal value of another spec section is near zero.

### F4 — Reliability: random failure is not the risk ✅ (new answer)

`scripts/reliability_model.py` (Phase 16) sums **1,005 FIT ⇒ MTBF ≈ 995,000 h ≈ 114 years** at 40 °C.
First *hard* wear-out is the LiFePO4 cell at **8 years**, then the gasket at 8, the RTC cell at 10, the
frontlight at 15.

**This settles a design argument for free: never add redundancy, add spares and service intervals.** A
redundant charger or a second RTC would be money spent against a curve that isn't the limiting one. The
model is one number per category precisely so a reviewer can attack an assumption instead of the total.

### F5 — No RMA, spares, or warranty model ⚠

Audit 3 flagged it; still absent. There is a maintenance *schedule* (`LONGEVITY_30Y.md` §4) but no
service-kit part numbers, no spare inventory, no warranty statement, no cost-of-service estimate. For a
30-year object this is not paperwork — it is the difference between "repairable" and "a claim".

### F6 — Regulatory: 4 filings, all "not started" ⚠

FCC Part 15 (unintentional radiator), CE RED (radio + EMC + safety), ISED (Canada), and **UN38.3** for
shipping the LiFePO4 pack. UN38.3 is a hard gate: no prototype with a battery ships by air without it,
and it needs cells plus a test house. Budget ~$8–15 k and 6–10 weeks; it is the longest-lead item in the
programme and it has no owner.

### F7 — `tools/archival/` still does not exist ⚠

Audit 3 named it the cheapest long-term win (pinned toolchain, offline build). Only
`tools/provision/setup_solardeck_os.sh` exists. Still open, still cheap, and it gets more expensive every
month the toolchain drifts.

## 2. What is genuinely strong

- **`STATUS.md` with `measured: 0` in bold** — most projects at this stage claim otherwise.
- **The 15-phase runner** (1.5 s) now enforces the docs, the BOM, the numbers, the firmware contract, and
  the reliability model. That is more verification than most shipped hardware repos have.
- **The register contract** (`solardeck_regs.h` + wire test) is the first artifact in the repo that
  proves a firmware behaviour rather than describing one.
- **Two decisions were reversed by evidence** (TMUX1575 4-vs-8 channel, MIPI-DSI video). The log of
  those reversals (`90-history/decisions.md`) is the most valuable document in the repo for a reviewer,
  because it shows the design can lose arguments.

---

## 3. What I would have Opus and Fable attack

Not "review the docs" — that is now low-yield. Attack these, in this order:

1. **The 2034 problem.** Is a socketed CM4 with a CM5 escape hatch actually credible for 30 years, or is
   the honest answer "this is a 10-year device and the 30-year claim is marketing"? This is a
   positioning question disguised as a supply-chain question, and it is the one I cannot answer alone.
2. **The 3.5:1 doc-to-code ratio.** Which half of the 41 specified daemons should never be built? A
   30-year device with 41 daemons is a maintenance liability; the argument for cutting to ~8 is strong
   and nobody has made it.
3. **Zero test points / zero measured values.** Is there a dev-kit path that produces *three* measured
   numbers (S2idle power, wake latency, keystroke latency) without a full carrier spin? Those three
   decide whether the pillars are real.
4. **UN38.3 and the battery.** Which cell, which test house, which schedule — and does the pouch cell
   choice survive it?
5. **The piezo reversal (ADR-020).** I descoped it for reliability; a second opinion on whether
   localized haptics are worth one fatigue site is genuinely open.

## 5. Bottom line

Three audits ago this repo had 10 blockers and no honest statement of what was real. It now has a
15-phase gate, a status page that admits zero measurements, a reliability model that says where to spend
money, and a firmware contract with a test.

What it does not have is a board. The next audit should be performed with a soldering iron, and the
highest-value thing anyone can do before that is kill half the daemon list and answer the 2034 question.
